## Verdict: **Aligned** — register all four, do not fix. Phase 3 does **not** gate on F9–F12.

All four are pre-existing, none is reachable from the fund's own client, none changes a number a
member or the treasurer ever sees, and in all four v2 is the better-behaved side. Reproducing v1
would mean **deliberately writing three defects into a fresh codebase** — an RFC violation, an
uncaught 500, and a double-faulting error logger — and in F11's case re-blessing a row the fund
would have to clean up by hand.

**No operator question is warranted for any of the four.** All are settled by domain reasoning; I
am not spending the operator's 28th question on them. The one place I do want the operator is
unrelated to F9–F12 and is at the end (it is a *confirmation*, not a blocker).

## F9 — `HEAD` returns an entity body in v1, none in v2 → **REGISTER**

**Ruling: register. No code change.**

Business reasoning:

* **No fund client sends `HEAD` at all.** The React app issues `GET`/`POST`/`PATCH`/`DELETE`; the
  treasurer's uploads are `PATCH`/`POST`; the scheduler and the Lambda talk to SQS/SES, not to the
  API. There is no member-facing or treasurer-facing process on this verb.
* **The only thing a client reads still agrees.** Status and `Content-Length` are identical on
  11/11 routes. A conforming client discards a `HEAD` body by definition (RFC 9110 §9.3.2), and any
  reverse proxy in front of v1 strips it before a real client sees it — so even in v1 nobody has
  ever observed these bytes.
* **v1 is the non-conformant side and the cause is not application code.** It is gunicorn 19.9.0's
  WSGI writer. "Fixing" v2 means making Node's HTTP server emit bytes it deliberately suppresses —
  fighting the runtime to reproduce a server bug, with no beneficiary.

Proposed **§5** row:

| # | v1 behavior | Change in v2 | Phase | Status |
|---|---|---|---|---|
| **D21** | gunicorn 19.9.0's WSGI writer emits the **full entity body on a `HEAD` request** — verified on a raw socket on 11/11 routes, DRF and plain-Django alike, including the 404 handler. RFC 9110 §9.3.2 says a `HEAD` response MUST NOT have content, so **v1 is the non-conformant side**, and the cause is the WSGI server, not any application code. | Node's HTTP server suppresses the body. **Status and `Content-Length` are byte-identical to v1 on every route** — the only difference is the bytes after the headers, which every conforming client and every intermediary discards. | cross-cutting (all phases) | ✅ **Accepted — register, do not reproduce.** No fund client issues `HEAD`; reproducing it means making Node emit bytes it deliberately suppresses, to re-create a server-level RFC violation with no beneficiary. Parity finding **F9**. |

## F10 — non-ASCII multipart boundary: v1 uncaught 500, v2 400 → **REGISTER**

**Ruling: register, keeping v2's 400. No code change. This registration is written to cover Phases
4–8, so the finding cannot be re-filed on the bulk loan upload or the file upload.**

Business reasoning:

* **The request is refused on both stacks and nothing is written on either.** The whole difference
  is which refusal the client is shown. No member's money, quota, loan or notification is touched.
* **A non-ASCII boundary cannot be produced by any real client.** The boundary is generated by the
  HTTP stack, not by the fund's code: browsers, `axios`, `curl` and every library emit ASCII. The
  treasurer's monthly TSV upload and (Phase 4) the bulk loan file both go through a browser file
  input. The **valid** multipart path is already proven byte-identical — round 3 matched v1's
  boundary contract on all 16 shapes including the 201/202 off-by-one — so the treasurer-facing
  flow is unaffected either way.
* **Reproducing it means deliberately introducing an uncaught exception.** v1's 500 is not a
  decision; it is `MultiPartParser.__init__` calling `content_type.encode('ascii')` on line 69,
  *before* `valid_boundary` on line 72, so a `UnicodeEncodeError` escapes DRF's handler. Porting
  that means writing a code path whose purpose is to crash — which also feeds ops alerting with a
  false alarm on every malformed request, for the life of the system.
* **v2's 400 is the same answer v2 already gives for every other invalid boundary.** Registering
  keeps one consistent rule ("a malformed boundary is a 400") instead of one 400 rule with a
  single non-ASCII exception.

Proposed **§5** row:

| # | v1 behavior | Change in v2 | Phase | Status |
|---|---|---|---|---|
| **D22** | A **non-ASCII `boundary`** is an **uncaught 500** (gunicorn's 141-byte HTML page, no `Allow`, no `Vary`): `MultiPartParser.__init__` does `content_type.encode('ascii')` at `multipartparser.py:69` *before* validating the boundary at `:72`, so a `UnicodeEncodeError` — not a `MultiPartParserError` — escapes DRF's exception handler. 49 cells across `/api-token-auth`, `PATCH /api/user`, `POST /api/user/activate/<id>`, `POST /api/user/power`. | **400** with DRF's parse-error detail, the same answer v2 gives for every other invalid boundary. Every **valid** boundary shape is unchanged and byte-identical (16/16, including the 201/202 length off-by-one). | cross-cutting — P3, and **P4 bulk loan upload / P8 file upload** | ✅ **Accepted — register, do not reproduce.** The request is malformed and refused on both stacks with **zero rows written on either**; only the shape of the refusal differs. No client can emit a non-ASCII boundary (the HTTP stack generates it, not the fund's code), so no member- or treasurer-facing process is affected. Reproducing it means writing a deliberately uncaught exception into v2 and alerting on it forever. **This row covers every multipart endpoint in Phases 4–8 — `manual-tester` must not re-file it there.** Parity finding **F10**. |

## F11 — file parts are not merged into `request.data`, and it changes a write → **REGISTER**

**Ruling: register. v2's current behaviour (500, no row) stands. Do NOT implement DRF's
`FILES`-into-`data` merge.**

This is the only one of the four that changes data, so I am answering both questions explicitly.

**(a) Is v1 creating a member whose first name is a filename a behaviour the fund could want? No —
and it is not a neutral row, it propagates.** `first_name` is not an inert column:

* it is the greeting in the **activation email** the new member receives (`create_user` builds
  `user_full_name` from it and mails immediately — v1 sent that mail in the tester's cell);
* it goes into the **fund-wide power-of-attorney letter** in formal Spanish, addressed to all 15
  members;
* it is the body of every **birthday notification** — `"Hoy está cumpliendo años a.txt Montañez"`,
  pushed to all other members;
* it appears in the member list every member reads on `GET /api/user`.

So v1's 201 does not produce a quietly-wrong row; it produces a row that emails the fund. And it is
**not fixable through the API**: `POST /api/user` is ADMIN-only (`permissions.py`, `UserView.POST: 0`)
and the only repair is another ADMIN `PATCH`, which is exactly the sort of manual clean-up this
migration exists to stop re-blessing. I checked the live data: all 15 `auth_user` rows carry real
names (`Miguel Ángel`, `N@CHO`, …) — **nothing in `fondodev` was ever created this way**, so nothing
depends on it.

**(b) Should v2 implement DRF's merge? No.** Two reasons, in order:

1. **The merge is what causes the bad row.** DRF merges `FILES` into `data`, `create_user` reads
   `obj['first_name']` with **no serializer** (`services/user.py:31`), and Django's `CharField`
   stringifies an `UploadedFile` to its **filename** — so the merge is precisely the mechanism that
   writes `a.txt` into a member's name. Implementing it means implementing the defect on purpose.
2. **v2's 500 is not an arbitrary refusal — it is v1's own missing-field behaviour.** Without the
   merge, `first_name` is simply absent from `data`; `create_user` has no serializer and no
   `KeyError` handler, so **v1 also 500s whenever a required field is absent**. v2 is therefore
   already reproducing v1's contract for "this field was not supplied" — it just classifies a file
   part as *not a value for a scalar field*, which is the correct classification for a fund member's
   name. Nothing new was invented here.

**Do not "improve" the 500 into a 400 either.** v1 500s on any missing field on this route, an
ADMIN's client can genuinely omit one, and the body shape is already registered (**P3-D6**). Turning
it into a 400 would create a *new* divergence on a reachable path to tidy an unreachable one.

**One thing this ruling owes Phases 4 and 8** — the real file-upload handlers must not rediscover
this. v1's `LoanView.patch` (P4) and `FileView.post` (P8) read their file out of `request.data`,
which only works in v1 *because* of the merge. v2's rule, already proven on the treasurer's TSV
(`PATCH /api/user` is 200 with identical rows on both stacks), is: **files come from
`request.files`, scalars from `request.body`; they are never merged.** That belongs in §4 as a rule,
not in a Phase 4 bug report — see the plan edits below.

Proposed **§5** row:

| # | v1 behavior | Change in v2 | Phase | Status |
|---|---|---|---|---|
| **D23** | DRF's `request.data` is `QueryDict` **merged with** `FILES`, so a **scalar field sent as a part carrying a non-empty `filename`** is read as an `UploadedFile`. `create_user` reads `obj['first_name']` with no serializer (`services/user.py:31`) and Django's `CharField` stringifies the file to its **filename** — so `POST /api/user` with `first_name` as a part named `a.txt` is **201**, creates a member whose first name is `a.txt`, and **sends them the activation email**. Verified live: `auth_user` 15 → 16. | **No merge.** Files are read from `request.files`, scalar fields from `request.body`. A scalar sent as a file part is therefore *absent*, and `create_user` 500s with **no row** — which is v1's own behaviour for an absent required field (no serializer, no `KeyError` handler). The **empty-`filename`** rule (Django treats it as an ordinary field) **is** ported, and the treasurer's real TSV upload is byte-identical on both stacks. | cross-cutting — P3, and **P4 bulk loan upload / P8 file upload** | ✅ **Accepted — register, do not reproduce.** `first_name` is not an inert column: it is the activation-email greeting, the name in the fund-wide power-of-attorney letter, the birthday-notification body, and the member list. v1's row emails the fund and is repairable only by another ADMIN `PATCH`. `POST /api/user` is ADMIN-only and **no live row was ever created this way** (all 15 names are real). Implementing DRF's merge would implement the defect on purpose. **`readUploadedFile` reading `request.files` is the standing pattern for P4 and P8** — see §4 rule 12c. Parity finding **F11**. |

## F12 — v1's 500 logger re-enters the failing parser and loses `Allow` / `Vary` → **REGISTER**

**Ruling: register. No code change.**

Business reasoning:

* **`Allow` and `Vary` on a 500 are read by nobody.** They matter on a 405 (which method should I
  have used) and on a cache (`Vary`). On an error page for a request the server could not parse,
  they carry no information any client acts on.
* **The trigger is unreachable from the fund's client.** It fires only on `POST /api/user/power`
  (power-of-attorney requests) with one of six malformed boundary shapes — absent, empty, 202-byte,
  trailing space, tab, non-ASCII — none of which a browser can produce. The **status is identical on
  all 208 malformed-multipart cells**; only the header set differs.
* **Reproducing it means porting a double-fault.** v1's behaviour is an accident of
  `log_response` → `get_post_parameters` → `request.POST` re-triggering the same parser failure
  *outside* Django's exception handling, so the response never reaches Django at all and gunicorn's
  page is served instead. There is no way to reproduce that in Nest except by building an error
  logger that re-parses the body and can itself throw — a defect with an operational cost (it hides
  the original traceback) and no benefit.
* **v2 is already correct and already reviewed.** Its answer is the DRF caught-500 shape that
  **F1 was fixed to produce**, with both headers. Changing it now would partially un-fix F1.

Proposed **§5** row:

| # | v1 behavior | Change in v2 | Phase | Status |
|---|---|---|---|---|
| **D24** | On the one Phase 3 view with a bare `except Exception` around a `request.data` read (`UserAppsView`), a `MultiPartParserError` is caught and answered as a DRF 500 — but Django's `log_response` then calls `get_post_parameters`, which re-reads `request.POST` and **re-triggers the same parser failure outside Django's exception handling**. The request never produces a Django response: gunicorn's 141-byte page is served with **no `Allow` and no `Vary`**, where the same view's other 500s carry both. Fires for the six boundary shapes v1 rejects × 12 bodies = 72 cells on `POST /api/user/power`. | The DRF caught-500 shape with `Allow: POST, OPTIONS` and `Vary: Accept, Origin` — i.e. the behaviour **F1 was fixed to produce**. Status is identical to v1 on all 208 malformed-multipart cells; only the header set on these six shapes differs. | cross-cutting — P3, and any later view with a bare `except` around a body read | ✅ **Accepted — register, do not reproduce.** `Allow`/`Vary` on an unparseable-request 500 are read by no client, and the trigger is unreachable from the fund's client. Reproducing it means porting Django's *error logger re-entering the failing parser* — a double fault that also hides the original traceback — and would partially un-fix **F1**. Residual of the **F1 / P3-D6** axis. Parity finding **F12**. |

## The process question — D19, D20, D11 on round 1's evidence

**Ruling: no separate re-run round. Fold a 5-cell spot check for D19 and D20 into the round-4
registration-confirmation pass. Accept round 1's evidence for D11 and move its verification to
Phase 9.**

The tester is right in principle — "unrefreshed for two rounds" is how a regression hides — but the
three are not equally exposed, and round 3 already refreshed more of this surface than the caveat
implies.

**What round 3 actually re-proved.** R3.5 re-ran the birthday `SchedulerTask` field by field
(byte-identical `type` / `run_date` / `repeat` / `processed` / `payload`, same heap-ordered
`user_ids` on both stacks) and the destructive side effect (a `personal` echo with `birthdate`
deleting 8 scheduler rows and creating 1, 626 → 619, on both). That is `createBirthdateNotification`
end to end. The **72-cell D1 matrix** also came back cell for cell identical. So the code that D19
and D20 live inside was exercised this round — what was *not* exercised is their two specific
branches.

**D20 — live, and it writes. Re-run it (2 cells).** `fondodev` has exactly two inactive members,
**id 3 (Fernando, birthdate 1974-03-02)** and **id 15 (Angi Paola, 1998-11-14)** — I confirmed both
live. A `PATCH` of either one's `personal` section carrying `birthdate` is v1 **500 + full
rollback** and v2 **200 + the edit persists**: a registered divergence where **v2 writes a row v1
does not**. That is the same risk class F6 was escalated for, it is reachable by an ADMIN today, and
round 3's version of the cell edits an *active* member, so it exercises the branch where the id
**is** in the list — the opposite of the guard. Two cells: PATCH user 3, PATCH user 15, restore.

**D19 — latent, cheap, and the clamp is a business-visible date. Re-run it (2 cells).** 0 of 15
members have a 29 Feb birthdate (confirmed live today), so nothing can regress in production — but
the deviation is that v2 **clamps to 28 February** rather than 500ing, and 28-vs-1-March is a date a
member sees in a birthday notification. It is 2 cells on a standing harness: set a member's
birthdate to 2000-02-29, PATCH, assert the `SchedulerTask.run_date` is 28 Feb, restore.

**D11 — accept round 1's evidence; verify in Phase 9.** Exercising it requires **fabricating a
duplicate `UserFinance` / `UserPreference` row in the shared `fondodev`**. This phase has already
had **three fixture incidents** (six `SchedulerTask` rows lost, plus two in round 2), and a
hand-fabricated duplicate in a shared database is exactly the shape that caused them. The payoff is
low: the v2 half that shipped is `findFirst` + `orderBy: {id: 'asc'}` — a read-ordering change with
unit coverage — and **nothing in v2 can create a second row**, so the branch is unreachable without
the fabrication. The half that actually matters, the physical `UNIQUE (user_id)`, is already
deferred to **Phase 9** by §4 rule 6. Verify both halves together there, on a database v2 owns.

**Why this does not need its own round.** Registering D21–D24 converts the tester's `FAIL` into a
`PASS` on §7, and that conversion should be recorded by the tester, not asserted by me — so there is
a short round-4 confirmation pass regardless. The four D19/D20 cells ride along at essentially zero
marginal cost, against an oracle that is already standing.

## Recommendation on the gate

**F9–F12 do not gate Phase 3.** With D21–D24 registered and §4 rule 12c added, Phase 3 goes to
`nestjs-reviewer`.

* **Gate 1 (`nestjs-developer`)** — no code change is required by this ruling. The four findings are
  closed by registration.
* **Gate 2 (`manual-tester`)** — the round-3 verdict is `FAIL` *solely* on §7 unregistered diffs.
  All four are now registered, so the finding set is empty. Round 4 is a **confirmation pass, not a
  re-test**: re-read D21–D24 against the round-3 evidence and add the four D19/D20 cells above.
* **Gate 4 (`business-analyst`)** — **Aligned**. Nothing in F9–F12 touches money, rounding, a rate,
  the 30/360 day count, a permission, or an email/notification recipient. F11 comes closest and cuts
  the safe way: v2 refuses to create a member record whose name would then appear in an activation
  email, a fund-wide Spanish letter and a birthday push.
* **Gate 5 (user)** — D21–D24 are registered as accepted; none is a product change requiring an
  operator decision.

Cutover being a hard switch is what makes this cheap: after the switch a v2-only behaviour has no
compatibility cost at all, and during parity testing the cost of these four is exactly four register
rows.
